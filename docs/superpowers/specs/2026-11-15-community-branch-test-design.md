## 怎么做

### 第一部分：合并，打 v4 镜像

1. 核心仓库 `UniXNU`：把 `crossdarwin/boot/sheng-firmware-compat`（比我们多 20 个提交）合进 `local/sheng-16g-macos`。`git merge-tree` 试过，没有冲突。
2. 设备仓库 `../UniXNU-sheng`：把 `crossdarwin/boot/sheng-firmware-compat`（多 14 个提交）合进 `local/sheng-12g-large-window`。
   - 唯一的冲突在 `board.toml` 两处，都是内存设置（窗口大小、窗口外的内存段表）。两处都保留本机的设置。
   - 合并前先处理没提交的改动：
     - 设备补丁 `patches/xnu-12377/sheng-text-fixup-verified-pagein.patch` 和 `series` 里那一行，提交到本地分支；
     - `feeds.toml`、`unixnu.lock` 的改动和社区分支的版本相同，先暂存起来，让合并带进来；
     - `drivers/Ath12kWifi` 子模块的改动，暂存起来；
     - 三个 `verification.json` 不提交、不暂存，原样留在工作区。
3. `../uefi-sheng` 不动。继续用 `local/sheng-12g-memory-map` 和已经构建好的新固件（`boot-bigwin.img`，1b 用过，能进桌面）。
4. `./unixnu build kernel payload`：会按社区的新版本重新下载、编译 Metal、蓝牙、Wi-Fi 等组件。
5. 做 7.5 GiB 载荷：参数和 `payload.bigwin-s1.img` 一样（窗口 `0x1E0000000`，下限 `0x920000000`，`memory-outside=0`）。用新固件转成 v4，文件名带 `bigwin-cd`。
6. 核对：
   - 补丁都打上了，包括 `cshash-signed-text-revalidation.patch` 和本机的设备补丁；
   - 参数行不带 `data-reset`；
   - 日常镜像的哈希没变。

### 第二部分：v0

7. 用合并后的 `./unixnu bootimg`：按社区的固定模板（校验值 `8fed0304…`，从 GitHub 发布页下载）打 v0 镜像，载荷用第 5 步的那份。文件名带 `v0-cd`。
8. 从内存启动它，记下引导程序的反应。

## 风险和处理

- 用户数据：合并后的载荷可能不认现在的数据卷，表现是黑屏加指针（社区报告里见过）。数据刚清空过，这时用菜单里新的"数据初始化"一项重建；它会再清空一次，做之前告诉用户。
- v0：本机引导程序 11-13 拒绝过 v0。如果这次接受了，模板里的固件是按 8 GiB 机器的内存布局做的。日常镜像的固件用的也是上游的内存表，在本机一直正常，所以多半没事，但没验证过。只从内存启动。
- 合并带进来很多改动，出了问题不好分是哪一项。真到那一步，再退回做法 A 单独测那个补丁。

## 约束

- 只从内存启动，不刷 `boot_a`。每次启动要用户在场说可以。每次进 fastboot 读两个槽位，a 在 4 或以下就补。
- 新文件名带 `bigwin-cd` 或 `v0-cd`，不覆盖日常文件。
- 芯片号不写进任何文件；`verification.json` 不提交；不推送。
- 合并、提交都只在本地分支上做。
